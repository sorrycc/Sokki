# Distribution, Community, and Virality

## Idea 1: `sokki://` One-Click Snippet Packs

**Pitch:** Register a `sokki://` URL scheme so any tweet, blog post, or README can link to a snippet pack that installs in one click. The friction from "I saw a cool snippet" to "it works on my Mac" collapses from ~90 seconds of copy-paste-edit-YAML to a single modal: "Install 14 Cursor prompts from @levelsio? [Install] [Preview]". This is the single highest-leverage thing a text expander can own, because every shared snippet becomes a distribution beacon.

**How it works:**
- `LSHandlers` registers `sokki://` (and `https://sokki.sh/pack/<id>` universal links) in the app bundle.
- URL carries either an inline base64 YAML blob (≤2KB packs) or a pack ID that resolves against `sokki.sh/pack/<id>.yaml` on R2.
- App shows a diff-style preview: trigger conflicts highlighted, destructive overwrites require explicit confirm, author handle + signature displayed.
- Installed packs live in `~/.sokki/packs/<author>/<pack>.yaml` — separate from user YAML, so `sokki pack update` is a real command.
- Every pack gets a shareable canonical URL auto-generated by the app ("Copy install link") — zero-friction creator side.

**Why it's accretive:**
- Every shared pack is a self-propagating ad. Install link in a tweet → each installer is a new node that will share their own packs.
- Creates the content moat: once `sokki.sh/pack/cursor-prompts-by-shadcn` exists, it's the canonical address. Competitors can copy the app, not the URL graph.
- URL scheme is the wedge Raycast used to win over Alfred — own the protocol, own the ecosystem.

**Risk / cost:** URL scheme hijacking is a real attack surface; signature verification + hard-coded author allowlist for featured packs is non-negotiable. Needs a hosted registry (even just R2 + a tiny Worker) from day one — ~2 weeks of work, ongoing hosting cost near-zero at Sokki's scale.

## Idea 2: Wall of Expansions (Live Leaderboard)

**Pitch:** `sokki.sh` landing page isn't a marketing site — it's a live, anonymized stream of the most-installed and most-triggered snippets this week, with one-click install on every row. Think "Hacker News front page, but for text expansions." The homepage itself becomes the growth loop: creators post packs to climb the board, visitors install from the board, installers become creators.

**How it works:**
- Opt-in telemetry (off by default, toggle in settings with plain-English copy) reports pack-level install + trigger counts — never snippet contents.
- Homepage surfaces: "Trending this week", "New from devs you follow on GitHub", "Packs for Claude Code / Cursor / K8s / Jira".
- Each row has author handle, install count, ▲ vote, and a single "Install" button that fires the `sokki://` scheme.
- Weekly email digest ("The 10 most-installed packs this week") — newsletters are a massive untapped dev distribution channel for menu-bar apps.
- Author profiles at `sokki.sh/@handle` aggregate their packs — personal brand incentive, which is what actually drives creators to publish.

**Why it's accretive:**
- Public ranking is the single most reliable creator motivator in history (GitHub stars, Product Hunt, HN karma, Dribbble). Ship the leaderboard and creators appear for free.
- Network effect compounds: more creators → better packs → more installers → more creators.
- Content moat: the leaderboard IS the moat. Any forker of the OSS can't clone the social graph.

**Risk / cost:** Privacy optics: telemetry on a text expander is radioactive if handled clumsily. Must be pack-ID-only, opt-in, open-sourced telemetry schema, and documented loudly. Gaming / spam — needs rate limiting and soft moderation from day one. Budget ~1 engineer-week for the abuse layer.

## Idea 3: Git-Native Team Packs ("fork this expansion")

**Pitch:** Treat snippet packs as git repos, not YAML blobs. A team pack is just `github.com/acme/sokki-pack` with a `sokki.yaml` at root; Sokki watches the repo, pulls on push, and merges into the active set. Now snippet management gets PRs, blame, diffs, code review, and — critically — the "Fork" button, which is the single most viral primitive humans have ever invented for text content.

**How it works:**
- `sokki pack add github.com/acme/eng-snippets` clones to `~/.sokki/packs/remote/` and watches via GitHub webhook → websocket, or 5-min poll fallback.
- Conflicts between a user's local triggers and team triggers resolved with namespaced prefixes (`;acme/standup` vs `;standup`) — configurable per-pack.
- A "Fork" button in the Sokki UI opens the pack's GitHub repo with fork pre-filled, then auto-wires the fork as the new source. Zero git CLI required.
- Team admins can enforce mandatory packs via an MDM-friendly config — enterprise wedge that pays the bills later.
- `sokki pack diff` shows YAML-level diff between your local and upstream — expansions become code, reviewable the same way.

**Why it's accretive:**
- Fork culture. Every forked pack is a new node in the graph AND a new GitHub repo that shows up in search for "cursor prompts", "k8s snippets", etc. Free SEO, compounding.
- Bottom-up enterprise distribution: one engineer forks an internal team pack, six teammates install it that week. Classic Slack / Notion loop applied to text.
- Uses GitHub as the distribution network instead of building your own — ship in days, not months, and inherits trust + identity + moderation from the host.

**Risk / cost:** Polling or webhook infra is non-trivial; start with 5-min poll to keep it dumb. Arbitrary git repos as a content source = security surface. Signed commits + an author allowlist for featured team packs is table stakes.

## Idea 4: `sokki record` — Turn Any Workflow Into a Shareable Pack

**Pitch:** A menu bar "Record Workflow" button that watches you type for 10 minutes and proposes a snippet pack: the 7 phrases you retyped, the 3 Jira ticket templates you pasted, the git commands you alias-wished. One confirm later, you have a pack. One more click, it's at `sokki.sh/pack/<id>`. This solves the cold-start problem nobody else has solved: getting non-creators to create.

**How it works:**
- Accessibility API (same permission Sokki already needs) records typing patterns locally — never leaves the machine until export.
- On-device frequency + n-gram analysis surfaces candidate snippets: "You typed `kubectl get pods -n production` 14 times this week. Trigger: `;kgpp`?"
- Auto-generates trigger suggestions from the content (first letters, smart abbreviations), which the user can edit inline.
- "Publish as pack" flow: add title, author handle, description, confirm diff of what will be made public. Signed and pushed to registry.
- Bonus: "Import from my shell history" and "Import from Raycast snippets / aText / TextExpander YAML" — steal the incumbents' user bases directly.

**Why it's accretive:**
- Turns every user into a pack author. Text expanders' fundamental growth problem is "users don't write snippets"; this reverses it.
- The "You typed X 14 times" moment is tweetable as hell — "Sokki just told me I typed `kubectl get pods` 87 times this week, here's the pack sokki.sh/pack/kubectl-survival". Content marketing writes itself.
- Defensible because it requires actual on-device measurement — a web-app competitor can't replicate this.

**Risk / cost:** Accessibility recording is the nuclear option for user trust. Must be explicit, time-boxed (red-dot indicator while recording), and 100% local until publish. Any slip here kills the project. ~3–4 weeks of focused work for the n-gram engine + UI. The hardest idea to build of the four, but the highest ceiling.

---

**Sequence:** Ship Idea 1 (URL scheme) in week 1 — it's a day of work and it unlocks everything else. Layer Idea 2 (leaderboard) on top as soon as you have 5 reference packs. Idea 3 (git-native) is your enterprise story for month 3. Idea 4 is the moonshot that makes Sokki unkillable, but only attempt it after the flywheel is already spinning.
