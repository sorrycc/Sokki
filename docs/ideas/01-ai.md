# AI / LLM Integration

## Idea 1: Inline AI Rewrites via Trigger Postfix

**Pitch:** Type a selection's text, suffix with a Sokki rewrite trigger like `;;pro`, `;;short`, `;;zh`, `;;fix`, and the selection is replaced in-place by an on-device LLM (Apple Foundation Models on macOS 15.1+, Ollama/MLX fallback). No menu, no popup, no context switch — the trigger IS the prompt. It turns every text field on macOS into an AI-editable canvas with zero UI, which is something TextExpander and espanso physically cannot ship because they have no LLM runtime.

**How it works:**
- New match kind in YAML: `ai: { prompt: "Rewrite professionally", model: "apple-foundation" }` alongside existing `trigger`/`replace`.
- On match fire, `TextInjector` sends Cmd+Shift+Left (or reads current selection via Accessibility API `AXSelectedText`) to grab the selected text, then streams it plus the prompt to `FoundationModels.framework` (on-device, zero-latency, zero-cost).
- Streamed tokens injected via the existing `injectViaKeys` path so the user sees the rewrite materialize live, one token at a time — feels magical.
- A new `AIRewriter` service sits alongside `VariableRenderer`; a `{{ai:...}}` variable also works inside normal replacements (e.g. `;;email` expands to a full email drafted from `{{clipboard}}`).
- Cancel key (Esc) aborts the stream and restores original selection via the existing `ExpansionUndoManager`.

**Why it's accretive:** Espanso/TextExpander are frozen in the "static string" paradigm. Raycast AI requires a popup and a subscription. Sokki would be the only tool where AI editing is literally part of your muscle memory — it becomes impossible to switch away because every document you write is faster. On-device means no API key, no cost, no privacy question — a moat Raycast cannot match without shipping their own runtime. Stickiness compounds as users build personal libraries of `;;tone-X` triggers.

**Risk / cost:** Foundation Models gating to macOS 15.1+ limits reach; need a clean Ollama/MLX fallback path. Capturing selection reliably across Electron/non-AX apps is the hard part (Cmd+C snapshot + clipboard restore works everywhere but feels slightly hackier). Effort: 2-3 weeks for MVP, another 1-2 for polish.

## Idea 2: Context-Aware Triggers (App & Content Scoping)

**Pitch:** The same trigger `;sig` expands differently in Slack (casual, "— cc"), Gmail (formal block), Terminal (shell comment), and Xcode (Swift doc-comment) — Sokki infers the *frontmost app + focused UI element + surrounding text* and routes through an LLM-generated variant, or the user's hand-authored per-context replacements. Triggers stop being global constants and become functions of *where* you're typing.

**How it works:**
- `TapContext` already knows the event source; extend it with `NSWorkspace.shared.frontmostApplication` and `AXUIElement` role (text field vs code editor vs terminal).
- YAML gains `contexts:` — array of `{ when: { app: "com.tinyspeck.slackmacgap", role: "AXTextArea" }, replace: "..." }`. First matching context wins, else default.
- A tiny local classifier (or FoundationModels zero-shot) maps the current app+role to a "register" (casual/formal/code/shell), letting a single `register:` attribute do the heavy lifting without hand-enumerating apps.
- Optional LLM path: one canonical replacement + `adapt: true` auto-rewrites the canonical form into the detected register on the fly, cached per (trigger, app) pair so it's instant after first use.
- Settings UI shows a live "current context" badge in the menu bar so users understand why a trigger behaved differently.

**Why it's accretive:** This is something espanso/TextExpander have bolted on half-heartedly via app filters, but none have *semantic register adaptation*. Once a user invests in one canonical library that auto-adapts, migrating away means rewriting every snippet N times for N apps. Strong lock-in, and it's a feature that gets better the more apps you use.

**Risk / cost:** AX role detection is flaky in Electron apps (Slack, VS Code, Discord) — need heuristics + bundle-ID fallback. Cache invalidation for adapted variants is tricky. Effort: 1-2 weeks for static per-app scoping, +1-2 weeks for LLM adaptation.

## Idea 3: Self-Writing Snippets from Your Typing History

**Pitch:** Sokki silently watches for repeated phrases you type (locally, privately, in a capped ring buffer), clusters them, and every Sunday morning a notification says: *"You typed 'Thanks, will circle back after standup' 14 times this week — assign it to `;cb`?"*. The app literally earns its own keep by proposing the snippets a user would never sit down and author. The library grows while the user sleeps.

**How it works:**
- Extend the existing 128-char `RollingBuffer` with a longer-term (off-tap-thread) encrypted n-gram store keyed by sentence-boundary detection — only phrases ≥ N chars, ≥ K repetitions across ≥ D days.
- On-device embedding (NaturalLanguage framework's `NLEmbedding` or a small MLX sentence-transformer) clusters near-duplicates so "Thanks, I'll circle back" and "Thanks — will circle back" collapse into one suggestion.
- Weekly (or threshold-triggered) menu-bar notification opens a lightweight review panel: accept → LLM proposes a mnemonic trigger (`;cb`), one-click commits to `suggested.yml`.
- Respect secure input + per-app blocklist (never mine passwords, 1Password, banking apps). All data local, encrypted with a key in Keychain, auto-purged after 30 days.
- Bonus: reverse flow — when the user types something that's *almost* an existing snippet's expansion, Sokki offers "Did you mean to type `;thx`?" as an unobtrusive nudge.

**Why it's accretive:** The #1 reason text expanders fail in practice: users never build their library. Sokki becomes the only expander with *negative onboarding effort* — the longer you run it, the more valuable it gets, automatically. This is a pure data/network effect on a single machine. Competitors would need to ship keystroke mining, and TextExpander/espanso's privacy stories can't justify it — but Sokki can because it's all on-device. Once users have 200 auto-curated snippets, they are never leaving.

**Risk / cost:** Privacy optics are the single biggest risk — needs extremely clear opt-in, visible "what I've learned" inspector, and a "forget everything" button front-and-center. Tuning the repetition threshold to avoid noise is hard (too low = spam, too high = useless). Effort: 3-4 weeks. This is the one idea where execution quality, not concept, determines whether users love or uninstall.

## Idea 4: Triggers That Call Agents, Not Strings

**Pitch:** A trigger like `;jira` pulls the Jira ticket ID from the URL of the frontmost Safari/Chrome tab, hits Jira's API, and drops a formatted summary. `;pr` reads the current `git` branch of the focused VS Code window, calls `gh pr view --json`, and inserts a markdown status. `;cal` asks `EventKit` for your next meeting. Replacements stop being strings — they're *tiny agents* that compose filesystem, shell, browser, calendar, and LLM tools. Your text expander becomes a universal "inject live data at the cursor" runtime.

**How it works:**
- New YAML match type: `action: { tool: "shell", run: "gh pr view --json title,body", transform: "{{ai: summarize as 3 bullets}}" }`.
- Ship a curated stdlib of built-in tools: `shell`, `http`, `eventkit`, `frontmost_url` (reads Safari/Chrome AX/AppleScript), `git` (discovers repo from frontmost Finder/terminal cwd), `clipboard_image_ocr` (Vision framework on `{{clipboard}}` when it's an image).
- Results flow through `VariableRenderer` so users can post-process with `{{ai:...}}` — e.g. `;standup` = git log since yesterday → LLM-summarize → inject.
- Sandboxed execution with per-action permission prompts (like Raycast extensions) and per-trigger timeouts; results cached briefly so rapid re-fires are instant.
- Ship a small MCP (Model Context Protocol) client so any MCP tool a user has — GitHub, Linear, Notion, whatever — becomes a `;trigger` with no plugin written.

**Why it's accretive:** This reframes Sokki from "text expander" to *"cursor as command line"* — a category move. Raycast lives in a launcher popup; Sokki lives in your cursor, which is where you already are. MCP support alone means every new integration the AI ecosystem ships becomes a Sokki trigger for free — massive free leverage on other people's work, and a genuine network effect. Espanso has shell execution but no context awareness or LLM post-processing; nobody has all three.

**Risk / cost:** Security is a real concern — arbitrary shell in a text expander is a footgun; need strong signed-trigger model and per-action confirmation for destructive ops. Scope creep risk is high — easy to over-build the tool registry. Effort: 2 weeks for shell+http+eventkit, 2 weeks more for MCP client, ongoing for the stdlib.
